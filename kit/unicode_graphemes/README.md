# Unicode grapheme core

Standalone Odin package, added for `slyx-lec.6.1` on the task branch (pending
integration). Implements **Unicode 15.1.0 default extended grapheme clusters**,
[UAX #29 revision 43, GB1–GB999](https://www.unicode.org/reports/tr29/tr29-43.html#Grapheme_Cluster_Boundary_Rules).
There is no normalization, locale tailoring, glyph/font restriction, line breaking,
shaping, pixel measurement, or SDL/UI/game/translation dependency.

## API and ownership

```odin
import graphemes "../unicode_graphemes"

result := graphemes.boundaries("éx", context.allocator)
if offsets, ok := result.([]int); ok {
    // {0, 3, 4}; text[offsets[i]:offsets[i+1]] is one complete EGC.
    defer delete(offsets, context.allocator)
}
```

- `UNICODE_VERSION` is `"15.1.0"`.
- `boundaries(text, allocator = context.allocator) -> Boundaries_Result` returns
  an **owned `[]int`**, including zero and the byte length. Empty text returns
  `{0}`. Offsets are UTF-8 **byte** offsets, not rune indices or display widths.
  The slice does not borrow the input; caller deletes it with the supplied allocator.
- `count(text) -> Count_Result` returns an `int`, zero for empty text. It uses
  exactly the same scanner as `boundaries`, without allocating (including through
  `context.temp_allocator`), and does not inherit UI text/line limits.
- Either operation can instead return `Invalid_UTF8 {byte_offset: int}`. The
  zero-based offset identifies the **start of the first ill-formed sequence**:
  an invalid lead/stray continuation byte, or the lead byte of an overlong,
  surrogate, out-of-range, truncated, or incorrectly continued encoding.
  No partial count/offsets are returned; intermediate offsets are freed on failure.
  Correctly encoded U+FFFD is valid, as are controls, noncharacters, private-use
  and unassigned scalars; display policy is outside this package.
- Input bytes are borrowed only during the call and never modified/retained.
  There is no mutable per-call global state. Allocation failure follows Odin's
  allocator policy, not a recoverable Unicode error contract.

The implementation reuses the pinned Odin strict UTF-8 decoder, explicitly
rejecting its one-byte error result, not the standard library's grapheme iterator.
Segmentation uses sorted property ranges and constant-size suffix state for
GB9c/GB11/GB12–13; it never rescans long combining/RI runs or allocates per cluster
in `count`. No numeric runtime performance guarantee is made.

## Data, provenance, license, regeneration

Original inputs are vendored unchanged in `data/`, downloaded 2026-10-25 from
`https://www.unicode.org/Public/15.1.0/ucd/` plus the paths below.
`generate.py` **v1** contains and verifies the full SHA-256 pins:

| Source | SHA-256 |
|---|---|
| `auxiliary/GraphemeBreakProperty.txt` | `a7e52eee647e52dc210b8719b4d7037276f4b353810293d69377fc46374cec3f` |
| `auxiliary/GraphemeBreakTest.txt` | `ed9c5e92fd0911ccbeeb63c97cb19c519ea272ff1112ce843abd991582dd848f` |
| `emoji/emoji-data.txt` | `d7aef489c8fe4c14f09ea5695200277c6b93ac82ac60845cdd2161b0d6835cc1` |
| `DerivedCoreProperties.txt` | `f55d0db69123431a7317868725b1fcbf1eab6b265d756d1bd7f0f6d9f9ee108b` |

Only GCB, Extended_Pictographic, and InCB properties are emitted. Adjacent equal
ranges are merged; omitted scalars use Other/false/None. Sortedness,
non-overlap and known property values are checked. The generator does not use
Python's Unicode database, download data, or silently follow `latest`.

Retain that notice with redistributed data/tables. The publisher's data/report
sources were consulted on that date; this is not a general vulnerability audit
or a promise to track later Unicode versions automatically.

From the repository root (Python 3.9+ standard library, checked with Python 3.14.7):

```sh
python3 kit/unicode_graphemes/generate.py
python3 kit/unicode_graphemes/generate.py --check
```

The first command deterministically writes `tables_generated.odin`; `--check`
verifies source hashes and exact generated bytes **without writing**. Generated
tables are included with the package; Python and data files are not needed by
runtime consumers. Updating Unicode requires an explicit version/algorithm/data/
pin/oracle update and fresh conformance checks, not merely regenerating with
different data.

## Checks

Pinned supported environment: Linux x86_64, Odin
`dev-2026-10-nightly:84bc3fc`. From the repository root:

```sh
odin check kit/unicode_graphemes -no-entry-point -vet -vet-style -vet-tabs -vet-semicolon
odin test kit/unicode_graphemes -out:/tmp/opencode/slyx-graphemes-test -vet -vet-style -vet-tabs -vet-semicolon
python3 kit/unicode_graphemes/generate.py --check
```

`core:testing` parses the original **complete 1187-case** Unicode 15.1.0
GraphemeBreakTest (embedded in the test binary, independent of generator output)
and compares exact byte offsets and count. Additional tests exercise every valid
Unicode scalar in isolation, malformed UTF-8/error offsets, rule-order and
ZWJ/RI/Indic/Prepend/control regressions, explicit allocator ownership, failure
cleanup, and allocation-free count. Tests are headless; they do not claim to
verify UI wrapping/ellipsis, glyph rendering, other `.6` tasks, or other platforms.
